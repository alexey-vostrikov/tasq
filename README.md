# tasq — локальный трекер задач для ИИ-агентов (ТЗ)

`tasq` — один статический бинарь на Rust: дерево работ (проект → эпик → задача → подзадача → …) в одном
SQLite-файле, MCP-сервер поверх stdio и CLI для человека. Предназначен для случая, когда работу ведут
несколько ИИ-агентов параллельно, а не один человек в браузере.

Трекер написан и работает: 0.9.0, схема v11, `make all` — 74 набора тестов. Этот файл — вход в
проект; нормативная часть (модель данных, статусы, аренды, MCP, надёжность) — в
[`docs/spec.md`](docs/spec.md), справочники генерируются из бинаря.

- имя проекта, пакета и бинаря: `tasq`
- репозиторий (локально): `~/DevOps/tools/tasq`; GitHub: `alexey-vostrikov/tasq`
- лицензия: MIT
- исходный класс задачи: `saga-mcp` (Node/npm), плюс приёмы из `mtix`, `rhizome-mcp`, `plandb`,
  `lific`, `backlog` — см. «Отношение к предшественникам».

## 1. Проблема, которую решает tasq

Агентская работа рассыпается на три вещи, которых нет в обычных трекерах:

1. **Контекст теряется между сессиями.** Jira и Linear рассчитаны на человека, который помнит план;
   агент — нет. Нужна структура, где сама иерархия несёт постановку: родитель объясняет «зачем»,
   ребёнок — «что именно сделать».
2. **Мёртвая работа.** Агент умирает на середине (таймаут, кончился контекст, упал процесс) и
   оставляет задачу в состоянии `in_progress` навсегда. Статус, который хранится, — ложь; статус,
   выводимый из живой аренды, — правда.
3. **Столкновения.** Два агента одновременно берут одну задачу или правят один файл. Блокировки
   нужны не на уровне «статус задачи», а на уровне «файл, каталог, порт, окно миграции».

`tasq` закрывает все три в одном бинаре, без сервера БД, без Docker и без сети.

## 3. Границы v1

**Входит в v1**

- Модель: проект → узел любого уровня (эпик, задача, подзадача, микро-задача), dot-notation ID.
- Аренды с истечением (claim/renew/release), производный `in_progress`, передача чекпойнта.
- Резервирование ресурсов: файлы, каталоги, glob, логические ресурсы (порт, слот деплоя, окно миграции).
- Зависимости `blocks` / `related` / `duplicates` / `discovered_from` / `split_from`, в том числе
  между узлами разных ветвей и уровней; детект циклов.
- Дедлайны, просрочка, burn-up по трём метрикам (штуки, очки, часы).
- Всё из saga: шаблоны с `{переменными}`, заметки 8 типов, комментарии с мягким удалением, лог
  активности, дашборд, «что дальше», пакетные операции, поиск, импорт/экспорт, `source_ref`, учёт времени.
- MCP-сервер stdio + профили инструментов + измеряемый бюджет схем в токенах.
- `tasq connect`: автоматическая прописка сервера в конфиги MCP-клиентов.
- CLI для человека: доска, дерево, burn-up, диагностика.

**Не входит в v1** (сознательно)

- Веб-интерфейс и GUI. TUI есть: `tasq tui` (см. `docs/tui.md`).
- Сетевая синхронизация, серверный режим на несколько пользователей, авторизация, роли.
- Облако, аккаунты, телеметрия — tasq не открывает сокет без явного флага.
- HTTP-транспорт MCP: `tasq serve --http` — только loopback, только под флагом, без TLS и без
  аутентификации; по умолчанию не поднимается (см. spec §13.3).
- Синхронизация команды через общий Postgres (есть у mtix) — не нужна без многопользовательского режима.

## 4. Термины

- **Узел (node)** — единица работы любого уровня: эпик, задача, подзадача, микро-задача. Одна таблица,
  различие — глубина и `kind`.
- **Dot-ID** — человекочитаемый идентификатор вида `TASQ-12.3.1`: путь в дереве, а не случайное число.
- **Попытка (attempt)** — один захват узла одним исполнителем. Аренда живёт внутри попытки.
- **Аренда (lease)** — право работать над узлом до момента `expires_at`; продлевается heartbeat-ом.
- **Исполнитель (holder)** — строка-идентификатор агента (`claude-code`, `codex/session-42`), не учётная запись.
- **Резерв** — заявка попытки на ресурс (файл, каталог, glob, логический ключ) с обнаружением конфликтов.
- **Эффективный статус** — вычисляемый из хранимого статуса и живых аренд/блокеров; в БД не хранится.
- **Чекпойнт** — свободный текст/JSON, который умирающая попытка оставляет следующей.

## Быстрый старт

Один файл, никакой настройки сервера: `tasq init` создаёт `.tasq/tasq.db` в текущем каталоге.

```
$ tasq init --key DEMO --name "Демо"
database: /tmp/qs2/.tasq/tasq.db
schema:   v11
project:  DEMO (created)

$ tasq add "Починить вход"
DEMO-1             idea        medium   -             0% -            Починить вход

$ tasq add "Добавить журнал" --parent DEMO-1
DEMO-1.1           idea        medium   -             0% -            Добавить журнал

$ tasq board
DEMO  open 2  done 0  overdue 0  leased 0

idea (1)
  DEMO-1         medium      0%            Починить вход

todo (1)
  DEMO-1.1       medium      0%            Добавить журнал
```

Узел — это и постановка, и адрес: `DEMO-1.1` читается как «первый ребёнок первого эпика», поэтому
после переноса узла по дереву адрес меняется, а `#id` остаётся. Взять узел в работу и закрыть:

```
$ tasq set DEMO-1.1 --status todo      # idea → todo: узел стал кандидатом
$ tasq next                            # что брать дальше и почему
1. DEMO-1.1           medium   Добавить журнал
   because priority medium

$ tasq claim DEMO-1.1 --holder me      # аренда: пока она жива, узел «в работе»
$ tasq release <token> --outcome completed
DEMO-1.1 -> done
```

Аренда — главная мысль инструмента: `in_progress` не хранится в узле, а выводится из живой аренды.
Агент, умерший на середине, не оставляет задачу «в работе навсегда» — через TTL узел сам
возвращается в очередь, а следующий получит его чекпойнт.

Для агента тот же трекер доступен по MCP:

```
$ tasq mcp --profile agent        # stdio, 31 инструмент, 3951 токен схемы
```

Прописать сервер в конфиг клиента — `tasq connect <client> --scope project`; список клиентов
печатает `tasq connect` без аргументов. HTTP-транспорт есть, но только по явному флагу и только
на loopback: `tasq serve --http 127.0.0.1:8787`.

Что происходило с трекером, отвечает одна команда — тем же числом человеку и агенту:

```
$ tasq stat --since 7d
since 2026-11-20T12:58:37.154Z: 2 call(s), 0 failure(s), 0 lock retry(ies), 24 мс всего
leases:    0 live, 1 expired open, 6 expired in window, 0 reservation(s); journal 0 КБ

operations:
  operation             calls      p50      p95      max   failed
  doctor                    1       22       22       22        0
  stat                      1        2        2        2        0
```

Метрики лежат в отдельном файле рядом с базой (`tasq-metrics.db`), а не в ней: счётчик в основной
базе вернул бы блокировку записи каждой читающей команде.

## 21. Критерии приёмки v1

1. `tasq init && tasq add … && tasq board` работает на пустой машине без сети и без Docker.
2. Dot-ID вида `TASQ-12.3.1` стабильны при работе и документированно меняются только при переносе.
3. Два агента не могут одновременно держать один узел; умерший агент не блокирует работу дольше своего TTL.
4. Конфликт резервов обнаруживается до начала работы и называет держателя и срок аренды.
5. Зависимость «задача в одной ветви → подзадача в другой» создаётся, а цикл — отвергается.
6. `tasq_next` объясняет выбор словами: приоритет, срок, что разблокирует.
7. `tasq burnup --ascii` показывает объём, готовое и линию цели; данные совпадают с логом.
8. `tasq tokens --max 6000` проходит на профиле `full`, а `read-only` укладывается в 1 600.
9. `tasq connect --dry-run` показывает корректный фрагмент для установленных клиентов; запись
   идемпотентна и не ломает существующие ключи.
10. Каждая функция saga из spec §13.2 имеет рабочий аналог (таблица соответствия — `docs/saga-parity.md`).
11. Экспорт → импорт в чистую БД даёт идентичный проект (dot-ID, рёбра, комментарии, заметки, шаблоны).
12. `cargo fmt`/`clippy -D warnings`/`test`/`deny`/`tokens` зелёные на чистом клоне.

## 21.1. Планируемый редизайн хранилища

Спека — `docs/storage-redesign.md`. Коротко, с доказательствами из этой базы:

- набор статусов переезжает из `CHECK` в справочник `statuses`: сейчас добавление статуса — это
  миграция с пересборкой `nodes` (v3: create/copy/drop/rename, выключение внешних ключей вне
  транзакции, перестройка FTS), а станет одной строкой данных;
- история статусов становится таблицей `node_status_history`: сейчас `burnup` достаёт день
  закрытия запросом по `activity_log` (`field_name='status' AND new_value='done'`), то есть
  зависит от того, каким путём записан переход;
- `path` перестаёт храниться и становится вычисляемым: перенос узла сейчас переписывает пути всех
  потомков, а будет менять только `parent_id`;
- `activity_log.entity_type` получает `CHECK` на шесть значений вместо свободной строки.

Не меняются: аренды с частичным уникальным индексом, производный `effective_status` во вьюхе,
TEXT-время в ISO, FTS5 с внешним контентом. Приёмка — дамп всей базы и восстановление без потерь
(задачи 2.2–2.5 в трекере).

## 22. Сборка, гейты и CI

Принцип: **на хосте rust-тулчейна нет, всё собирается в контейнере на базе Debian 11 с тулчейном
1.99.1**, и локальные гейты, `act` и GitHub Actions используют одну и ту же базу. База задаёт порог
glibc готового артефакта: на bookworm это 2.34, и бинарь не стартует на Astra/Debian 11 (2.31).

- `Dockerfile` — двухступенчатая сборка: `FROM rust:1.99.1-slim-bookworm` (тулчейн + rustfmt/clippy)
  → `FROM rust:1.90-bullseye` с деревьями rustup/cargo, скопированными из первой ступени. Тега
  `rust:1.99.1-bullseye` не существует (официальные bullseye-варианты кончились на 1.90), поэтому
  образ собирается из этого файла (`make image`), а не берётся готовым: «локальный образ с нужным
  именем» — это зависимость от чужой машины. libc в бинаре приходит из базы — 2.31.
  Bullseye в архиве: apt переключён на `archive.debian.org` с `Check-Valid-Until=false`, иначе любой
  `apt-get install` падает кодом 100 на 404 от `deb.debian.org`.
- `make` (по умолчанию) — `fmt` + `clippy` + `deny` + `test` + `tokens` + `docs --check` +
  `glibc-check`; `make build` — release-бинарь;
  `make smoke` — `init` + `doctor` во временном каталоге внутри контейнера; `make act` — прогон
  workflow на хосте.
- `cargo-deny` ставится готовым musl-бинарём (0.20.2) одним скриптом `scripts/install-cargo-deny.sh`
  и в `Dockerfile`, и шагом CI: две копии логики установки разъехались бы, и «проходит локально»
  перестало бы что-либо значить. Скрипт сверяет `sha256` скачанного архива.
- `deny.toml`: `[advisories]` — любая уязвимость и любой yank роняют сборку, `ignore = []`;
  `[licenses]` — только реально встречающиеся в дереве лицензии (MIT, Apache-2.0, Unicode-3.0,
  Unlicense, Zlib), снятые `cargo deny list`, а не список «на будущее»: новая лицензия — повод
  посмотреть на зависимость. `[sources]` разрешает только crates.io.
- Кэш cargo — именованный том `rrl-cargo-bullseye` (`CARGO_VOL`), общий с соседним `rust-rest-ldap`:
  реестр качается один раз на машину, а `target` у каждого проекта свой (`/cargo/target-tasq`).
  Том создаётся docker'ом от root, поэтому `cache-init` выставляет владельца под хостовый uid —
  иначе первый прогон падает `failed to create directory …: Permission denied`.
- Образ проверяется, а не собирается по ходу: `image-check` падает с подсказкой `run make image`,
  если образа нет (иначе `pull access denied` читается как проблема реестра).
- `.github/workflows/ci.yml` — job `check` с `container: rust:1.90-bullseye`; версия компилятора
  ставится из `rust-toolchain.toml` (`rustup default 1.99.1`), а не берётся из тега образа: шаги:
  тулчейн → компоненты (rustfmt, clippy) → `cargo-deny` → `fmt --check` → `clippy -D warnings` →
  `cargo deny check` → `test` → пол покрытия → `build --release` → smoke (`init` + `doctor --json`
  с проверкой `"ok": true`) → порог glibc → бюджет схем → актуальность `docs/`. Тот же файл
  исполняет `act` с хоста.
- Покрытие (`make cov`, шаг «Coverage floor»): `cargo-llvm-cov` с `--fail-under-lines 90`.
  Порог — **пол, а не цель**: он не мешает добавлять код, но не даёт выпустить «написали и не
  проверили». Сейчас 95,9 % строк (9 852 измеренных, 406 непокрытых); остаток — не ветки логики,
  а недостижимые защитные строки: разбор ошибок `?` в местах, где запрос составлен из проверенных
  значений, `unreachable!` для команд, обработанных до открытия базы, и `continue` в импорте для
  записей, которые уже отбиты проверкой до записи. `cargo-llvm-cov` ставится скриптом
  `scripts/install-cargo-llvm-cov.sh` с закреплённым хешем (у проекта нет файла контрольных сумм,
  поэтому хеш для x86_64 записан в скрипте, а для aarch64 установка честно отказывается).
  `cov` не входит в `make all`: инструментированная сборка пересобирает всё дерево.
- Подводный камень `act`: шаги он запускает через `sh -e` (это dash), поэтому `set -euo pipefail` падает
  `Illegal option -o pipefail`. У шага smoke явно указан `shell: bash` — на GitHub Actions поведение
  не меняется, в `act` работает.
- Порог glibc — часть контракта артефакта и проверяется гейтом, а не выясняется из ошибки
  загрузчика у пользователя: `make glibc-check` (`scripts/check-glibc-floor.sh`) читает максимум
  символов `GLIBC_*` через `objdump -T` и сравнивает версии по номеру, а не строкой. Факт на текущей
  сборке — `GLIBC_2.30` при пределе 2.31; шаг CI повторяет ту же проверку.

## 23. Документация (`docs/`)

Справочники не пишутся руками: `tasq docs` снимает их с самого бинаря и с пустой базы,
созданной текущими миграциями.

| файл | источник | что внутри |
| --- | --- | --- |
| `docs/cli.md` | описание CLI (clap) | все команды, их флаги, значения по умолчанию и описания |
| `docs/mcp-tools.md` | каталог `tools/list` | 48 инструментов, доступность по профилям, стоимость в токенах, обязательные аргументы |
| `docs/schema.md` | свежая база | фактические `CREATE TABLE`/`CREATE VIEW`/`CREATE INDEX` и версия схемы |

Нагрузочный гейт — `make perf` и шаг «Read budget on a ten thousand node project» в CI:
фикстура 10 000 узлов (глубина 4, веер 3, 250 корневых эпиков) строится заново в отдельном
каталоге и не касается живой базы, а бюджеты названы числом. Замер (release, сорок прогонов
после прогрева, в одиночку), в миллисекундах: доска 138–177, `ls` 135–180, `next` 18–36,
`ls --fields` 152–200. То есть на десяти тысячах узлов доска читается не «мгновенно», а за
десятую-две десятых секунды. Раньше эту цену TUI платил четыре раза в секунду: 62 % ядра в
простое на такой базе. Теперь экран спит в ожидании письма (поток ввода и наблюдение за
каталогом базы), а после чужой записи перечитывает не доску, а затронутые узлы и их предков —
6 мс против 177 мс. В простое — ноль чтений доски и ноль обращений к базе (см. `docs/tui.md`).

Гейт сравнивает с ЛУЧШИМ прогоном, а не с медианой или хвостом: на одном коммите медиана
доски ходила 153 → 177, p95 — 212 → 502, а минимум держался 138–177. Разброс этот — паузы
общего докер-хоста, а не стоимость запроса (код между прогонами не менялся), и гейт,
краснеющий от чужой нагрузки, отключают через неделю. Минимум — оценка самой стоимости:
сорок прогонов гарантированно содержат один, не попавший на паузу. Форму дерева, статусы и даты задаёт
`bench::Spec` детерминированно: две сборки с одним `Spec` дают одинаковый состав, иначе
сравнивать замеры между прогонами было бы не с чем.

Гейт: `tasq docs --check` сравнивает файлы на диске с тем, что получилось бы сейчас, и возвращает
код 3 при расхождении. Он стоит в `make docs` (входит в `make all`) и шагом «Reference docs are
up to date» в CI. Смысл в том, что справочник команд, написанный отдельно от кода, расходится
с ним на первой же правке флага, и расхождение замечает не автор, а тот, кто по нему работает.

`docs/saga-parity.md` — исключение: это не справочник, а разовый разбор API `saga-mcp@1.19.0`,
он написан руками и генерировать его не из чего.

Число тестов здесь не написано намеренно: оно меняется на каждой правке, а руками правленный
счётчик расходится с прогоном молча — ровно та же болезнь, из-за которой справочники `docs/`
генерируются из бинаря. Актуальное число печатает `make all`, и оно же в выводе CI. Единственные
числа, которые README с тех пор повторяет, — количество инструментов и стоимость профилей, и их
сверяет `tasq docs --check` (гейт падает, если разошлись).

Ветка (`branch`) — рабочий фильтр, а не украшение: `add --branch`, `set --branch` (без значения
— текущая ветка из `git symbolic-ref --short HEAD`), `set --no-branch` снимает её в NULL,
`ls --branch` и `next --branch` отбирают узлы этой ветки, `B` на доске включает тот же фильтр.
Сравнение точное: `feat/x` не задевает `feat/x-fix`. Вне репозитория значения нет — фильтр не
включается, и об этом сказано в stderr, потому что полный список без объяснения читался бы как
«в этой ветке весь проект».

## 25. Решения по открытым вопросам

Вопросы, стоявшие до M1, закрыты реализацией; здесь зафиксировано, чем именно, и что осталось.

| вопрос | решение | где видно |
| --- | --- | --- |
| идентификатор исполнителя | строка `holder` от клиента, без привязки к проекту: один агент может работать в нескольких | `attempts.holder`, `claim --holder`, `tasq_claim` |
| дедлайн эпика против дедлайна задачи | хранятся отдельно, эпик свой срок не агрегирует: `min(сроки детей)` скрыл бы отставание детей | `nodes.due_date`, `tasq risk` |
| `shared`-резервы | оставлены: без них нельзя заявить «читаю, но не пишу»; конфликт `shared` только с `exclusive` | `Mode::Shared`, `tests/resource.rs` |
| часы против очков | `weight` по умолчанию `1`, метрика burn-up выбирается флагом, а не настройкой проекта | `burnup --metric count\|points\|hours` |
| публикация | публичный репозиторий GitHub, MIT; в crates.io — отдельным решением | `LICENSE`, `Cargo.toml` |
| TUI | `tasq tui`: доска в терминале, `--once` печатает один кадр (спека — `docs/tui.md`) | `tasq board` для скриптов |

Открытый пункт один: **HTTP-транспорт MCP-сервера не реализован**, сервер работает только по stdio.
`tasq connect --url` пишет адрес, который должен обслуживать внешний прокси (например `mcp-proxy`);
сам `tasq` порт не слушает. Пока это не сделано, `--url` — способ подключить прокси, а не встроенный
HTTP-режим, и README не должен создавать обратного впечатления.
