# Журнал ub-mode: воронка статусов, проекты, сборка

Три темы рабочего дерева: воронка `idea → backlog → todo`, проект как сущность иерархии
(без проекта по умолчанию), тулчейн на Debian 11 с гейтом порога glibc. Код первых двух тем
был написан до включения ub-mode, поэтому фазы применены к нему как к проверяемому состоянию:
сначала доказательства (мутации, контрольные опыты), потом метрики, потом коммиты.

## First make it work → Then make it right

Падающих тестов «наперёд» для готового кода не писалось (это была бы имитация TDD). Вместо
этого каждая новая точка решения проверена МУТАЦИЕЙ: подмена кода, прогон своего теста,
откат обратной правкой и `grep`, подтверждающий, что мутация снята (`git checkout --` на
неотслеживаемых файлах молчит, поэтому не применялся).

| мутация (сайт решения) | тест, который обязан покраснеть | результат |
| --- | --- | --- |
| `select(None)` снова молча берёт первый проект | `work_goes_to_the_project_named_by_the_selector` | `FAILED 0 passed; 1 failed`, остальные 18 отфильтрованы |
| `Kind::initial_status` → `Todo` (воронки нет) | `dot_ids_follow_the_tree` | `FAILED` |
| аргумент `project` у вызова игнорируется | `a_session_without_a_project_refuses_instead_of_picking_one` | `FAILED` |
| `todo` убран из входов в `deferred` | `deferred_is_reachable_from_open_states_and_leaves_them` | `FAILED` |
| строка `review` в README теряет `blocked` | `readme_transition_matrix_matches_the_code` | `FAILED`, сообщение называет пару |

Гейт glibc проверен КОНТРОЛЬНЫМ ОПЫТОМ на настоящем плохом артефакте, а не рассуждением:
старый bookworm-бинарь (`GLIBC_2.34`) отвергнут с кодом 1, bullseye-бинарь (`2.30`) проходит.
Отдельно проверено, что версии сравниваются как версии: при пределе `2.9` бинарь `2.30` обязан
быть отвергнут, и мутация `sort -V` → `sort` ложно пропускает его — поэтому негативный контроль
встроен в `make glibc-check` и в шаг CI.

## Что нашлось и исправлено по ходу проверки

- **README §7 обещал переходы, которых не было в коде** (`deferred → idea`) и молчал о тех, что
  код разрешал (`idea/backlog → blocked`). Исправлено в обе стороны, и теперь расхождение ловит
  тест `readme_transition_matrix_matches_the_code` (разбирает таблицу README и сравнивает с
  публичным `can_transition`).
- **Ветка `Deferred => &[…]` не была покрыта ни одним тестом** — подмена списка проходила молча;
  добавлен `deferred_is_reachable_from_open_states_and_leaves_them`.
- **Ранний возврат `from == to`** в `can_transition` не проверялся; добавлен
  `the_same_status_is_always_allowed`.
- **`patch` с нечётким совпадением молча переписал путь в Makefile:** цель `glibc-check`
  ссылалась на `$(CACHE)/target/...`, где `CACHE` уже не определён, и проверка падала
  `no binary at /target/release/tasq`. Замечено прогоном, а не чтением диффа; после правки —
  `make -n` и реальный запуск.

## Остаток, названный прямо

- `Kind::depth()` не вызывается нигде (`grep -rn '\.depth()' src tests` пуст). Это публичный
  метод библиотеки, поэтому удаление — отдельное решение о смене API, а не уборка в этом шаге.
- Дизъюнкции в ассертах (`assert!(a || b)`) в новом коде отсутствуют; три существующих
  (`src/budget.rs:131`, `tests/docs.rs:185`, `tests/cli_coverage.rs:316`) не трогались: они вне
  темы шага.
- Автотеста на сам `scripts/check-glibc-floor.sh` в репозитории нет: он проверяется прогоном в
  `make` и в CI, включая негативный контроль.
- Мутационный замер (`cargo-mutants`) на этом дереве не гонялся: точки решения проверены
  ручными мутациями (таблица выше), полный прогон — отдельная работа с отдельным образом.

# Шаг: автодополнение оболочки (`tasq completions`)

Порядок — TDD: сначала `tests/completions.rs` (четыре теста), прогон красный по ОЖИДАЕМОЙ
причине (`unrecognized subcommand 'completions'`), потом `clap_complete` и подкоманда.
Скрипт собирается из `Cli::command()`, то есть из того же описания, что разбирает аргументы.

| мутация (сайт решения) | тест, который обязан покраснеть | результат |
| --- | --- | --- |
| алиас `completion` убран | `the_singular_alias_works` | `FAILED` |
| `--out` игнорируется (всегда stdout) | `out_writes_the_script_to_a_file` | `FAILED` |
| команда обрабатывается ПОСЛЕ открытия базы | `every_supported_shell_gets_a_script_without_a_database` | `FAILED` (DB_NOT_FOUND) |

Живая проверка на установленном бинаре (bash, `_tasq` вызывается так, как её зовёт `complete -F`):
`tasq cl` → `claim`, `tasq claim --pro` → `--project`, `tasq completions <TAB>` → `bash elvish fish
powershell zsh`, `tasq dep <TAB>` → `add rm ls graph`.

Что осталось: вывод скрипта в `head`/`less` падает `failed printing to stdout: Broken pipe`
(паникует `print!` в std) — это общее поведение всех команд с длинным выводом, а не только
дополнений; лечится обработкой `EPIPE` на границе вывода отдельным изменением.

# Шаг: ссылки с ключом разрешаются в любой проект

TDD: сначала `tests/cross_project_refs.rs` (6 тестов), прогон красный по ожидаемой причине
(`PROJECT_REQUIRED` у `show DEV-1.1` без проекта и `INVALID_REF` с чужим ключом), потом код.

## Мутации (каждая падает ровно на своих тестах, откат сверен по sha256)

| мутация | упало |
| --- | --- |
| ключ ссылки игнорируется, проект всегда из контекста | 3 теста: чтение, запись, MCP |
| `project::for_reference` не смотрит на ключ (нужен селектор) | `a_reference_with_a_key_needs_no_selector`, `an_unknown_key_…` |
| `update` снова грузит по id в проекте контекста | `a_write_through_a_keyed_reference_lands_in_its_project` |
| MCP не берёт проект из ключа аргумента-ссылки | `mcp_resolves_keyed_references_in_both_session_states` |

Мутация «вернуть исходный дефект» получилась полезнее новой: она воспроизвела настоящую ошибку
первой реализации — ссылка читалась, а правка падала `NODE_NOT_FOUND #4`, потому что `load_by_id` и
`activity::log` фильтруют по проекту. Отсюда `resolve_with_project`: разрешение возвращает ПРОЕКТ
вместе с узлом, и дальше всё — журнал, перечитывание, дети — идёт в проекте адреса.

## Изменение поведения, названное прямо

Два старых теста сменили ожидаемый КОД, и оба — в сторону более точного:
- `edge::link` на узел чужого проекта давал `INVALID_REF` (симптом того, что ключ не читался) —
  теперь узел разрешается, и отказ приходит от правила: `CROSS_PROJECT_EDGE` с именем узла;
- `resolve("OTHER-1")` давал `INVALID_REF` — теперь `PROJECT_NOT_FOUND` со списком ключей.

Оба обновления подписаны в тестах причиной, а не подогнаны под вывод.
