# Редизайн хранилища: что меняется и почему

Статус: спека (TASQDEV-2.1). Основание для задач 2.2–2.5. Код не меняется этим документом.

## Что есть сейчас (по фактической схеме, v3)

Таблицы: `projects`, `nodes`, `attempts`, `reservations`, `edges`, `comments`, `notes`,
`templates`, `activity_log`, `burn_snapshots`, `meta`.
Представления: `v_node_effective`, `v_node_progress`, `v_blockers`, `v_overdue`,
`v_attempt_hours`, `v_node_hours`. FTS: `nodes_fts`, `notes_fts` (внешний контент + триггеры).

Живой объём на 2026-11-10: 2 проекта, 80 узлов, 61 попытка, 74 комментария, 411 записей журнала,
28 резервов, 4 ребра. То есть текущий дизайн проверен на объёме, где всё ещё быстро — и это
важно: редизайн делается не ради скорости, а ради **отсутствия хрупких мест**.

## Проблемы, которые действительно мешают (с доказательством)

### 1. Смена набора статусов требует пересборки `nodes`

`CHECK (status IN (…))` — единственный способ держать допустимые значения в SQLite, но он
неизменяем: добавление `idea`/`backlog` потребовало миграции v3 с
`CREATE TABLE nodes_v3 / INSERT / DROP / RENAME`, выключением внешних ключей вне транзакции,
`legacy_alter_table` и перестройкой FTS. Это 120 строк SQL и четыре подводных камня, каждый из
которых рвёт данные молча (каскадный `DROP TABLE` уносит `attempts`, `edges`, `comments`, `notes`).

**Решение: справочник статусов вместо списка в `CHECK`.**
```sql
CREATE TABLE statuses (
  name     TEXT PRIMARY KEY,
  rank     INTEGER NOT NULL UNIQUE,   -- порядок воронки, а не алфавит
  terminal INTEGER NOT NULL DEFAULT 0,
  accepts  TEXT NOT NULL DEFAULT '[]' -- какие статусы допустимы следующим (JSON-массив имён)
);
CREATE TABLE nodes (… status TEXT NOT NULL REFERENCES statuses(name) …);
```
Тогда новый статус — `INSERT` в справочник, без пересборки таблицы. Матрица переходов тоже
переезжает в данные (`accepts`), а проверка остаётся в коде (`check_transition`), потому что
`accepts` нужен и для подсказок. Цена: согласованность справочника и кода надо проверять тестом
(иначе разойдутся, как разошлись README и матрица в §7).

### 2. История статусов живёт в прозе журнала

`burnup::transition_day` достаёт день закрытия запросом
`activity_log WHERE field_name='status' AND new_value='done'`. Это работает только пока все пути
записи статуса пишут именно такую пару — а их два (`transition` при ручном переходе, `completed`
при завершении через аренду), и добавление третьего (импорт, restore) тихо ломает ряд.

**Решение: `status_transitions` отдельной таблицей.**
```sql
CREATE TABLE node_status_history (
  id        INTEGER PRIMARY KEY AUTOINCREMENT,
  node_id   INTEGER NOT NULL REFERENCES nodes(id) ON DELETE CASCADE,
  from_status TEXT REFERENCES statuses(name),
  to_status   TEXT NOT NULL REFERENCES statuses(name),
  at        TEXT NOT NULL,
  actor     TEXT,
  cause     TEXT NOT NULL CHECK (cause IN ('manual','lease_completed','lease_released',
                                           'import','restore','force'))
);
CREATE INDEX idx_status_history_node ON node_status_history(node_id, at);
```
Журнал остаётся журналом (что произошло), история статусов — фактом (когда узел стал `done`).
Burn-up читает факт, а не текст. Тест: ряд burn-up пересчитывается и совпадает с прежним на
истории живой базы.

### 3. `path` — хранимое производное

`nodes.path` вычисляется при создании и **переписывается у всех потомков** при переносе. Отсюда:
`UNIQUE(project_id, path)`, `path GLOB` в поддеревьях, риск расхождения (перенос переписал корень,
потомков нет), и отдельный тест «старый адрес резолвится» — самая частая ошибка.

**Первоначальное решение — «`path` становится представлением» — отменено по замеру.**

Замер на синтетической базе (2 015 538 узлов, 8 уровней, fanout 6, схема v8, тот же SQLite):

| операция | хранимый `path` | вычисляемый (рекурсивный CTE) |
| --- | --- | --- |
| порядок дерева, `ORDER BY path LIMIT 100` | **0.2 мс** (индекс `UNIQUE(project_id, path)`) | 3 764 мс |
| полный список дерева (2 млн строк) | 1 758 мс | не выполнимо в разумное время |
| поддерево узла (55 987 потомков) | 258 мс (`path GLOB`) | **115 мс** (обход по `parent_id`) |
| перенос с перезаписью путей 9 330 потомков | 165 мс | 1 `UPDATE` |

Что из этого следует:

1. **Полностью вычисляемый `path` — регресс на три порядка.** Рекурсивный CTE материализует всё
   дерево ДО сортировки, поэтому `ORDER BY path LIMIT 100` превращается из 0.2 мс в 3.7 с: индекс
   перестаёт работать, а `ls` сортирует именно по пути. При 80 узлах разница невидима — при
   десятках тысяч она делает команду непригодной.
2. **Обход по `parent_id` быстрее `path GLOB` в 2.2 раза** на поддереве (115 против 258 мс):
   GLOB сканирует диапазон индекса и перепроверяет каждую строку, обход идёт по `idx_nodes_parent`.
   То есть отказ от строковых операций выгоден **в подзапросах на поддерево**, а не в сортировке.
3. **Перезапись путей при переносе не является узким местом**: 165 мс на 9.3 тыс. потомков, и
   перенос узла с таким поддеревом — редкая операция. Тезис «перенос дорог» замером не
   подтверждается.

**Решение: `path` остаётся хранимым, но перестаёт быть единственной опорой.**

- Уникальность адреса дублируется структурой: `UNIQUE(project_id, parent_id, seq)` — индекс, при
  котором два узла не могут получить один адрес даже если строку пути испортят.
- Операции над поддеревом переведены с `path GLOB` на рекурсивный обход по `parent_id`
  (`src/tree.rs`): дело не в «2.2 раза», а в сложности. План запроса показал, что `path GLOB`
  вообще не использует индекс по пути — он сканирует все узлы проекта, поэтому его стоимость
  росла с размером БАЗЫ: 130 мс даже на поддереве из 43 узлов при базе 2 млн. Обход по
  `idx_nodes_parent` растёт с поддеревом: 0.0 мс на тех же 43 узлах.
- Запрет переноса «в себя» уже считается обходом по `parent_id` (2.6.6), а не префиксом строки.
- Расхождение «корень переехал, потомки нет» закрывается одной транзакцией и тестом, а не сменой
  модели: перезапись идёт в том же `write_tx`, что и `UPDATE parent_id`.

Цена отказа от представления: правило «один источник истины» не выполнено — путь остаётся
производным, но хранимым. Это осознанный компромисс: он оплачен скоростью сортировки, и замер
показывает, что цена альтернативы на три порядка выше.

Материализованное представление с триггерами (кэш пути) остаётся возможным вариантом, если
появится нужда в обходе без `parent_id`, — но вводить его «на всякий случай» замер не поддержал.

### 4. `activity_log.entity_type` — свободная строка

`entity_type TEXT NOT NULL` со значениями `node`, `comment`, `note`, `edge`, `project`,
`template` в коде, без ограничения в схеме. Опечатка в коде (`"coment"`) не отбивается, а строки
с ней живут годами.

**Решение: `CHECK` на шесть значений.** Дешёво, обратной совместимости не ломает.

## Что НЕ меняется (и почему)

- **Аренды и резервы.** Частичный уникальный индекс `uq_attempts_live` + `BEGIN IMMEDIATE` —
  проверено гонкой восьми процессов, десять кругов, ровно один победитель. Менять нечего.
- **`effective_status` во вьюхе по времени.** Производный статус от аренды — правильная форма:
  нечему рассинхронизироваться. Переезд в хранимую колонку потребовал бы фонового обновления и
  дал бы окно неверных данных.
- **TEXT-время в ISO.** Сортируется лексикографически и сравнивается как строка — этого
  достаточно; переход на UNIX-время сломал бы читаемость базы через `sqlite3` без выгоды.
- **FTS5 с внешним контентом.** Работает, триггеры есть; при пересборке таблицы их надо
  пересоздавать — это учтено в миграции и останется учтено.
- **Хранение dot-ID (не хранение, сборка из ключа и пути).** Правильно: переименование ключа
  проекта двигает все адреса одним `UPDATE`, и это задокументированное следствие.

## Порядок работ

1. **2.2 Дамп всей базы.** (сделано) Без него редизайн с пересборкой делать нечем. Фактический состав
   `export` (проверено прогоном): `project` (единственный, не список), `nodes`, `edges`,
   `comments`, `notes`, `templates`, `snapshots`. **Не попадают**: остальные проекты базы,
   `attempts` (аренды), `reservations`, `activity_log`. Поэтому восстановить из экспорта можно
   только один проект и без истории: `burnup` и `time` на восстановленной базе будут пустыми,
   а `activity_log` — начатым с нуля. Дампу нужен режим «вся база».
2. **2.3 YAML.** (сделано) Тот же документ в человекочитаемом виде: дамп читается глазами и
   правится руками.
3. **2.4 Путь апгрейда.** (сделано как `tasq load`) дамп → схема текущей версии → заливка одной
   транзакцией → отчёт потерь с адресами узлов и кодом выхода 3, если потери есть.
4. **2.5 Приёмка на живой базе.** Копия → проверка счётчиков и выборочных узлов → переключение →
   бэкап v3 остаётся. Откат — восстановление из дампа, не `cp` файла (WAL).
5. **2.6 Схема v4.** Делается несколькими миграциями, а не одной: `0004` (справочник статусов,
   история переходов, сессии, строгий `entity_type`), `0005`–`0008` (истёкшая аренда, причина
   `lease_expired`, причина `created`, сторож цикла в представлении прогресса). `path` как
   представление ОТМЕНЕНО замером — см. §3.
   Разделение вынужденное и осознанное: `0004` меняет только структуру и переносит данные,
   `0005` переписывает все запросы, которые трогают `path` (13 мест с `path GLOB` плюс
   представления). Одна миграция на оба изменения означала бы, что откат после пересборки таблиц
   идёт вместе с откатом рефакторинга — а это две разные причины для отката.

## Критерии приёмки редизайна

- Дамп живой базы восстанавливается без потерь: счётчики по каждой таблице совпадают,
  `PRAGMA foreign_key_check` пуст, `integrity_check` = ok.
- Добавление нового статуса — одна строка в `statuses` и ни одной миграции `nodes`
  (проверяется тестом: `INSERT` в справочник и переход в новый статус по матрице).
- Перенос узла переписывает потомков в одной транзакции, и путь остаётся хранимым — решение
  принято по замеру (см. §3): полностью вычисляемый `path` даёт 3.7 с на `ORDER BY path LIMIT 100`
  против 0.2 мс, что делает `ls` непригодным. Вместо смены модели: `UNIQUE(project_id, parent_id, seq)`
  как структурная гарантия уникальности адреса и обход по `parent_id` вместо `path GLOB`
  в операциях над поддеревом (2.6.11).
- Burn-up считает историю из `node_status_history` и **не** читает `activity_log`;
  проверка — тест, в котором журнал пуст, а ряд строится.
- `doctor --check` чист на восстановленной базе; MCP отвечает на весь каталог инструментов.
- Глубина: 17-й уровень отбивается `DEPTH_LIMIT` и в дереве, и в шаблоне (предел один,
  `node::MAX_DEPTH`); проверка предела на длину пути отсутствует, а не ослаблена.
- История: `export` → `import` в чистую базу даёт **тот же** ряд burn-up, что и источник
  (сейчас даёт `done 0`); `import --from-saga` даёт по одной записи `cause='import'` на узел;
  `burn-up` без истории печатает «история неизвестна», а не `-0.0`.
- Матрица: новый статус — `INSERT` в `statuses` плюс правка кода, без миграции `nodes`; тест
  сверяет справочник с `Status::all()`; подсказка `INVALID_TRANSITION` перечисляет допустимые
  статусы, а не отправляет в README.

## Сессии

`sessions` заведена в v4, но не заполнялась: `attempts.session_id` оставался пустым, и три
параллельных процесса `hermes` были неразличимы — у них общий `holder`. С привязкой `next` к
проекту это стало неудобством, а не косметикой: склейка сессий означала бы, что они тянут друг
друга из проекта в проект.

Решено:

- **Идентификатор приходит снаружи.** MCP-процесс заводит свой при старте (`session::new_id`,
  16 случайных байт), CLI берёт из `TASQ_SESSION`. Ядро не может отличить один вызов от другого
  и не придумывает идентификатор: нет его — нет привязки, `next` перечисляет проекты как есть.
- **Привязка ставится взятием работы**, а не просмотром: «работала в проекте» ≠ «посмотрела на
  проект». Привязка по просмотру тянула бы сессию туда, куда она заглянула случайно.
- **Явный `--project` сильнее привязки** и её не меняет: «покажи только этот проект» — осознанный
  запрос, а не сигнал о том, где сессия работает.
- **Правило `next`**: пока в своём проекте есть что брать — только своё; когда пусто — остальные
  проекты, с пометкой в ответе (`origin`: `affinity` / `fallback` / `unbound`).
- **Сессия регистрируется до вставки аренды.** `attempts.session_id` — внешний ключ на
  `sessions`; заводить сессию после вставки значило бы получить отказ внешнего ключа.

## Открытые вопросы — закрыты

Решения приняты; в коде они ещё не отражены, поэтому раздел читается как задание.

### Глубина: 16 уровней, сторож в представлении, порог в коде

- `node::MAX_DEPTH = 16`. Отдельного предела на длину пути больше нет: при 16 сегментах dot-ID
  укладывается в 255 байт с запасом, и второе правило (`MAX_PATH_BYTES = 200`) только создавало
  невидимый порог, наступающий раньше первого.
- Предел остаётся проверкой в коде (`DEPTH_LIMIT` с внятным текстом), а не `CHECK`: смена порога
  не должна требовать пересборки `nodes` — это ровно та ошибка, которую v4 убирает у `statuses`.
- В представлении путей рекурсивный член **прекращает работу** на `depth < MAX_DEPTH`. Это не
  проверка входа, а сторож завершаемости: порченый `parent_id` или цикл в базе, записанной
  другой версией бинаря или руками, не должны вешать чтение. Два разных дела: порог записи
  (код) и сторож чтения (SQL).
- `load` глубину не проверяет: состояние есть состояние. Глубже предела — предупреждение в
  отчёте, а не потеря строк.
- Отдельная задача: запрет переноса в собственного потомка. Сейчас он держится на префиксе
  строки `parent.path.starts_with(node.path + ".")` (node.rs:844); без хранимого пути нужен
  обход вверх по `parent_id`, и тест «перенос в собственного потомка отвергается» обязан
  остаться, иначе цикл появится молча.

### История статусов: переносить, когда файл её несёт

Причина решения — замер на бинаре 0.4.0: `export` проекта → `import` в чистую базу даёт
`done 0.0` при том, что закрытый узел на месте. История живёт только в `activity_log`, а он в
экспорт проекта не входит.

- `load` (дамп `tasq-dump`) — история переносится как есть, с `cause` и `actor`. Это наше
  состояние, sha256 сверен.
- `import` файла `tasq.export.v1` — формат расширяется таблицей истории, и дальше ведёт себя как
  `load`. Конверт получает поле `history: present|absent`: «в файле истории нет» и «у узла
  переходов не было» — разные факты, и различать их по пустому массиву нельзя.
- `import --from-saga` — одна синтетическая запись на узел: `cause='import'`,
  `from_status=NULL`, `to_status=<текущий>`, время = `created_at` узла, а не момент импорта.
  Узел не появился сейчас, он сейчас доехал.
- `cause` в таблице истории: `manual`, `lease_completed`, `lease_released`, `unblock`, `gc`,
  `import`, `restore`. Пять путей записи статуса (node.rs, lease.rs ×2, edge.rs ×2) обязаны
  писать факт каждый — иначе ряд burn-up снова начнёт зависеть от совпадения текста в пяти
  местах.
- `burn-up` обязан различать «закрытых нет» и «история неизвестна»: печатать
  `done 0 (история неизвестна)` вместо `-0.0`. Сегодняшний `-0.0` — ещё и след арифметики
  `0.0 - x`; отрицательный ноль в отчёте выглядит как значащее число.
- Провенанс (`origin: own|foreign`) в таблицу **не** добавляется: это свойство события импорта,
  а не статуса узла, и его место — в одной записи журнала «импортировано из файла X».

### Матрица переходов: в коде, справочник без `accepts`

- `statuses(name, rank, terminal)` — только для того, чтобы новый статус был `INSERT`-ом, а не
  пересборкой `nodes`. Порядок воронки (`rank`) и признак закрытости (`terminal`) — данные, потому
  что их читают доска и отчёты; допустимые переходы — код, потому что это правило проверки.
- `can_transition` остаётся чистой функцией без базы: 90 пар, 50 разрешённых (56 %), 300 строк
  тестов проверяют свойства, а не строки таблицы. Данные не тестируются — они лежат.
- Справочник заполняется миграцией из `Status::all()`, тест сверяет порядок и состав: иначе
  доска и справочник разъедутся так же, как разъехались README и матрица в §7.
- Подсказка к `INVALID_TRANSITION` называет актуальный список («из `todo` можно в `in_progress`,
  `blocked`, `deferred`, `done`, `cancelled`»), а не отправляет в README: MCP-агент README не
  читает и получает отказ без выхода.
- `requires_force` (реоткрытие закрытого) переезжает в политику проекта — `projects.metadata`.
  Это первое, что действительно захочется менять без релиза, и к структуре дерева оно не
  относится.
